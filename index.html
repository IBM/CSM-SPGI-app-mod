Lab Environment

The environment for this workshop is composed of:

  • OpenShift cluster
  • RHEL bastion

Both are shared amongst all participants. The RHEL bastion is pre-configured with the scripts, assets and CLIs you will need to complete this workshop. All these will be placed under your user home directory.

3. Expose the application

Reference

https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/networking_overview/understanding-networking

3.1 Cluster IP

Let's start exposing the application internally using a ClusterIP service type. As you did before, create a file called was-service1.yaml with this content:

apiVersion: v1
kind: Service
metadata:
  name: websphere-liberty-service1
  namespace: nsX
spec:
  selector:
    app: websphere-liberty-app
  type: ClusterIP
  ports:
    - protocol: TCP
      port: 9080
      targetPort: 9080

Tip

The indentation is very important. Pay attention when executing the copy and paste. If you have problems with the copy and paste, all the files used in the labs are in the artifact folder under the user home folder.

Once you have the file created, execute:

Command
oc create -f was-service1.yaml -n nsX
Output
service/websphere-liberty-service1 created

If everything went well, your service should be deployed, and the application can accessed from inside the cluster (this means other pods running in it):

3.2 Ingress

Reference

https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/networking_operators/configuring-ingress

Once you have a service, you can create an Ingress object to expose the application to consumers outside the OpenShift cluster. It uses an OpenShift service (ClusterIP) to know the internal IPs used by the application.

The Ingress Controller used by default in OpenShift is an HAProxy, but there are more ingress controllers available (i.e. F5 Ingress Controller).

Create a file called was-ingress.yaml with this content:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: websphere-liberty-ingress
  namespace: nsX
spec:
  rules:
    - host: websphere-liberty-app-nsX.apps.XXXXXXX.XXX.techzone.ibm.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: websphere-liberty-service1
                port: 
                  number: 9080

Tip

The indentation is very important. Pay attention when executing the copy and paste. If you have problems with the copy and paste, all the files used in the labs are in the artifact folder under the user home folder.

Important

The ingress subdomain XXXXXXX.XXX must be the one assigned to the cluster. You can find it in the URL of the OpenShift web console in your browser. See the example below:

In the example from the image, XXXXXXX.XXX is 6807747a6d9f36b0be0add5c.eu1. Therefore, the URL in the yaml file must be websphere-liberty-app-nsX.apps.6807747a6d9f36b0be0add5c.eu1.techzone.ibm.com

Once you have the file created, execute:

Command
oc create -f was-ingress.yaml -n nsX
Output
ingress.networking.k8s.io/websphere-liberty-ingress created

If everything went well, your service should be deployed:

Command
oc get ingress -n nsX
Output
NAME                        CLASS    HOSTS                                                                             ADDRESS                                                               PORTS   AGE
websphere-liberty-ingress   <none>   websphere-liberty-app-ns29.apps.65f05030777e25001ee8fdfa.ocp.techzone.ibm.com     router-default.apps.65f05030777e25001ee8fdfa.ocp.techzone.ibm.com     80      17s

With this Ingress object, OpenShift has configured the ingress controller to route traffic from internal routers to the application/deployment in the cluster.

The "rule" is that all the requests made for the hostname http://websphere-liberty-app-nsX.apps.XXXXXXX.XXX.techzone.ibm.com must be routed directly to the pods selected by the service websphere-liberty-service1. This enables, for example, sticky sessions. There are other options to configure the rules not only by hostname. For example, it is also possible to use the path.

Now access the ingress URL to access your application. As you are using the cluster's ingress subdomain, you can access it directly without further configuration:

http://websphere-liberty-app-nsX.apps.XXXXXXX.XXX.techzone.ibm.com

Tip

Remember, it is exposed over http rather than https.

You can also try with curl:

Command
curl -s http://websphere-liberty-app-nsX.apps.XXXXXXX.XXX.techzone.ibm.com | grep WebSphere
Output
<title>WebSphere Liberty 19.0.0.9</title>
            <h2>WebSphere Liberty 19.0.0.9</h2>

2. Storage Classes

Reference

3. Create a Persistent Volume Claim

First, delete all artifacts created in the previous lab:

Command
oc delete -f was-deployment.yaml -n nsX
Output
deployment.apps "websphere-liberty-app" deleted

You will use the WebSphere Liberty sample application again, but externalizing the logs directory to persistent storage. That way, logs will be maintained after pod restarts.

You are going to create a dynamic Persistence Volume via the Storage Class. Let's do it by creating a Persistent Volume Claim, go to Storage > PersistentVolumeClaims. Then click Create PersistentVolumeClaim:

Change the following values and click Create. Please make sure you just ask for 10 MiB:

  • StorageClass: ocs-storagecluster-cephfs
  • PersistentVolumeClaim name: was-volume1
  • Access mode: Shared access (RWX)
  • Size: 10 MiB

Alternatively, you can copy the following content on the Edit YAML section, updating the red marked texts:

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: was-volume1
  namespace: nsX
spec:
  accessModes:
    - ReadWriteMany
  resources:
    requests:
      storage: 10Mi
  storageClassName: ocs-storagecluster-cephfs

And press the Create button.

If everything goes well, the PVC should appear with Bound status.

Info

Since you created a PVC from scratch using a StorageClass, an underlying PV was automatically created.

If you ever need to link a PVC with an existing PV, you can use a selector. In the Persistent Volume Claim you can specify the PV label like this:

selector:
  matchLabels:
    app: myPersistentVolume

If you do not specify a label or a Storage Class, the bind is done randomly always considering the requirements of the PVC and the characteristics of existing PVs. If no matching PV is found it will remain in Pending status.

4. Use the persistence volume claim in an application

Let's deploy the WebSphere Liberty image again, but this time mapping its /logs directory to the external persistence volume you have created. The yaml definition should now be familiar to you except for the new lines related to persistent storage.

Create a file named was-deployment-pvc.yaml with the following content (or use the one on the artifacts folder already created for you):

apiVersion: apps/v1
kind: Deployment
metadata:
  name: websphere-liberty-app
  namespace: nsX
spec:
  selector:
    matchLabels:
      app: websphere-liberty-app
  replicas: 1
  template:
    metadata:
      labels:
        app: websphere-liberty-app
    spec:
      containers:
        - name: websphere-liberty-app
          image: websphere-liberty:19.0.0.9-webProfile8-java11
          ports:
            - containerPort: 9080
          volumeMounts:
          - mountPath: "/logs"
            name: was-persistence
      volumes:
        - name: was-persistence
          persistentVolumeClaim:
            claimName: was-volume1
      initContainers:
      - name: permissionsfix
        image: alpine:latest
        command: ["/bin/sh", "-c"]
        args:
          - chown 1001:0 /test;
        volumeMounts:
        - name: was-persistence
          mountPath: /test

2. Checking the application's health

Sometimes the container is running but the application may be in trouble. OpenShift can query the application status and restart it if it doesn't return a HTTP 200 OK code.

The sample application you deployed has two other endpoints:

  • /health: will check an instance variable and return HTTP 200 or HTTP 500 based on its value.
  • /infect: will change the instance variable value to force HTTP 500 in the /health endpoint.

After invoking the /infect endpoint, the application will start returning a HTTP 500 code on its /health endpoint.

Let's add that health check to your deployment descriptor so OpenShift uses it to verify the application is actually running healthy. You can edit the YAML file and apply the change or edit it from the OpenShift console. Let's do the second option this time to learn a new way of modifying deployed elements.

Info

Of course, all the changes applied through the OpenShift console will be lost if you start from scratch, replacing the deployment with the original YAML files without the changes.

Go to Workloads > Deployments in the OpenShift web console. You should see your deployed application. Then click its name:

Go to the YAML tab.

You will see a lot of new fields that you didn't have in the original YAML file. All those fields are added automatically by OpenShift, but your original fields are all present.

Modify the deployment descriptor to add the field livenessProbe. This element is used by OpenShift to poll the application asking for its status. It can be an HTTP request, a TCP invocation, or a shell command. You are going to use an HTTP check: if the response has a status code less than 200 or greater than 400, the pod will be restarted automatically.

OpenShift checks the readinessProbe first to make sure the container has started. Then, it checks the livenessProbe periodically to ensure it continues returning a ready status.

These are the specs for livenessProbe and readinessProbe that you need to place properly in your deployment definition:

          readinessProbe:
            httpGet:
              path: /health
              port: 8080
              scheme: HTTP
            initialDelaySeconds: 5
            timeoutSeconds: 30
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3            
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
              scheme: HTTP
            initialDelaySeconds: 5
            timeoutSeconds: 30
            periodSeconds: 10
            successThreshold: 1
            failureThreshold: 3

Important

Make sure the indentation is set properly. Otherwise, OpenShift will yield errors.

Lab 7 - Operators

Reference

https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html/operators/operators-overview

Operators are software extensions to OpenShift that make use of custom resources to manage applications and their components.

The Operator pattern aims to capture the key aim of a human operator who is managing a service or set of services. Human operators who look after specific applications and services have deep knowledge of how the system ought to behave, how to deploy it, and how to react if there are problems.

People who run workloads on OpenShift often like to use automation to take care of repeatable tasks. The Operator pattern captures how you can write code to automate a task beyond what OpenShift itself provides.

Demystifying the operators, all the automation must be implemented by the operator provider, so there is no out of the box upgrade, backup, restore or other features just because something is an operator, those features must be coded in the operator by the operator provider. The automation available out of the box is the native automation of OpenShift for things like health check, scalability, load balancing and so on. An operator is a container developed by a software provider running in OpenShift looking to the state of "proprietary/custom objects (CRDs)" and taking actions depending on the values of that object.

Based on the features offered by the operators they are catalogued in these groups:

OpenShift supports and installs out of the box the Operator LifeCycle Manager (OLM), OLM provides a set of features to help in the installation and management of Operators.

https://github.com/operator-framework/operator-lifecycle-manager

Info

OLM extends OpenShift to provide a declarative way to install, manage, and upgrade Operators and their dependencies in a cluster.

  • Red Hat Operators: Red Hat products packaged and shipped by Red Hat. Supported by Red Hat.

  • Community Operators: Optionally visible software maintained by relevant representatives in the operator-framework/community-operators GitHub repository. No official support. Access to https://github.com/operator-framework/community-operators/tree/master/community-operators to view all available operators.
  • Custom Operators: Operators you add to your own quay.io app repository. If you have not added any Custom Operators, the Custom category does not appear in the web console on your OperatorHub.

6. Create backup

Command
sed -i "s/todo/$namespace/g" config/backup-todo.yaml
oc create -f config/backup-todo.yaml

7. Verify backup status

Command
oc get backup/$namespace -n openshift-adp -o jsonpath='{.status}'|jq

8. Use velero cli to set the backup

Command

9. Use velero cli to check the backup

Command
velero get backup

10. Create schedule backup with the following command

Command
sed -i "s/todo/$namespace/g" config/schedule-todo.yaml
oc create -f config/schedule-todo.yaml

11. Check result after schedule is created

Command
oc get schedule/$namespace -n openshift-adp -o jsonpath='{.status}'

12. Let’s create a disaster in the environment by deleting some content

Command
oc delete deployment/todo-db -n $namespace
oc delete pvc todo-db -n $namespace

13. List backups and get the name

Command
oc get backup -n openshift-adp

14. Configure the restore

Edit restore-todo.yaml and replace spec.backupName with name from previous step. To perform the restore, follow the next steps:

  1. Look for the backup name obtained from the previous command:

    Command
    BACKUP_NAME=<backup name>

  2. Create and execute the restore:

    Command
    cat config/restore-todo.yaml | sed 's/todo/'$namespace'/' | sed 's/BACKUP_NAME/'$BACKUP_NAME'/' |  oc create -f -

15. Check the result of the restore

Command
oc get restore/$namespace -n openshift-adp -o yaml|grep -A8 'status:'

This is an example of the output of the command to check the restore result:
